---

## 1. Purpose

This artifact establishes the controlled receiving and direction procedure for any AI, contributor, agent, or fresh development session entering the KOSFintech project.

Its purpose is to prevent a newly onboarded AI from interpreting an already-established subject as new work, confusing developmental evidence with production implementation, treating structural similarity as semantic equivalence, bypassing established semantic ownership, or inventing a next step that has not been established by the project.

This artifact is a navigation and control mechanism. It does not replace domain declarations, semantic contracts, engineering frontiers, validation records, governance records, Git, or the Continuity Corpus.

---

## 2. Governing Principle

A fresh AI MUST establish project direction before proposing consequential work.

The AI MUST NOT infer:

- absence of implementation = absence of prior engineering work;
- presence of documentation = production implementation;
- successful code or tests = constitutional authority;
- structural similarity = semantic equivalence;
- repeated terminology = shared domain meaning;
- an existing platform capability = authority to use it in another domain;
- an unresolved question = permission to decide it;
- an untracked artifact = disposable material;
- a Library artifact = current repository state;
- a historical checkpoint = current checkpoint;
- a convenient abstraction = established DSL construct.

The project state MUST be established before action.

## 5. Subject Routing

Before acting on any subject, identify:

1. **What is the subject?**
2. **Which domain owns it?**
3. **Where has it already been recorded?**
4. **Which artifact is its semantic owner?**
5. **What related artifacts depend on that semantic owner?**
6. **What has already been established?**
7. **What remains unresolved?**
8. **What is the implementation status?**
9. **What validation evidence exists?**
10. **What is the next controlled frontier, if one is actually established?**

If these answers cannot be established, the AI MUST inspect further before proposing consequential change.

---

## 6. Subject Locator Pattern

For a major subject, construct a bounded locator:

**SUBJECT**
What is being discussed?

**DOMAIN OWNER**
Which independently bounded MOS/domain owns the meaning?

**SEMANTIC OWNER**
Which artifact establishes the meaning?

**ENGINEERING EVIDENCE**
Where is recurring engineering exposure documented?

**CROSS-DOMAIN EVIDENCE**
Where has correspondence or recurrence been demonstrated?

**IMPLEMENTATION STATUS**
Implemented / Not Implemented / Partially Implemented / Unknown.

**AUTHORITY STATUS**
Authority effect, if any.

**PRODUCTION DEPENDENCY**
Production dependency, if any.

**VALIDATION STATUS**
What has actually been validated?

**UNRESOLVED FRONTIER**
What remains deliberately unresolved?

**NEXT CONTROLLED ACTION**
What is explicitly established as the next step?

The locator is a routing mechanism, not a replacement for the underlying artifacts.

## 7. Registered Work Protection

Before proposing a new capability, abstraction, operational mechanism, entity, relationship, workflow, or DSL construct, the AI MUST determine whether related work has already been registered.

The AI MUST search:

- current domain artifacts;
- engineering exposure artifacts;
- semantic contracts;
- change records;
- DSL Resource Base;
- validation records;
- continuity records;
- relevant Git history.

The AI MUST distinguish:

**Already registered**
from
**implemented**
from
**validated**
from
**authorized**.

A subject may already be extensively registered while remaining unimplemented.

The absence of production code MUST NOT cause the AI to restart an already-established developmental frontier.

---

## 8. Semantic Ownership Rule

When multiple artifacts mention the same concept, the AI MUST determine which artifact owns its semantics.

Mentioning a concept does not confer semantic ownership.

Dependent artifacts MUST coordinate with the established semantic owner rather than redefining the concept.

Example:

For CDA_MOS membership, the established semantic owner is the:

- CDA Membership Frontier; and
- CDA Membership Semantic Contract.

The Organizational Structure Frontier coordinates with that established membership meaning and MUST NOT independently redefine it.

---

## 9. Domain Independence

SMOS, CMOS, CDA_MOS, and future MOS domains are independently bounded domains.

The AI MUST NOT infer semantic inheritance merely because:

- structures look similar;
- fields have similar names;
- workflows recur;
- engineering mechanisms are reusable;
- a capability already exists elsewhere.

Engineering reuse MAY be evaluated independently.

Semantic inheritance MUST NOT be assumed.

In particular:

**SMOS Student ≠ CDA Member**
**SMOS Teacher ≠ CDA Capacity**
**CMOS Member ≠ CDA Member**
**CMOS Membership ≠ CDA Membership**

Structural recurrence is evidence for investigation, not permission to collapse domain meaning.

Technical capability is not constitutional authority.

- software capability;

- application role;
- administrator permission;
- API;
- audit record;
- technical attribution;
- account ownership;
- workflow completion;
- test result;
- Git commit;
- Library preservation.

Where governance or constitutional authority is relevant, the AI MUST locate the governing authority record before treating an action as authorized.

## 14. Unresolved Means Unresolved

An unresolved concept MUST remain unresolved until sufficient evidence and an explicit controlled decision establish it.

The AI MUST NOT convert:

- a candidate into a requirement;
- a possibility into an invariant;
- a proposed lifecycle into an implemented lifecycle;
- a structural relationship into authority;
- a workflow suggestion into executable behavior;
- an engineering convenience into domain law.

Where evidence is insufficient, preserve the unresolved state.

---

## 15. Recovery and Temporary Artifact Protection

Untracked files MUST NOT be deleted merely because they are untracked.

The AI MUST first classify them as:

- developmental;
- recovery;
- temporary;
- historical;
- superseded;
- current;
- unknown.

Recovery copies and  artifacts are evidence of development history and MUST NOT automatically be treated as current implementation.

Cleanup requires deliberate classification and decision.

---

## 16. Next-Frontier Rule

The AI MUST derive the next action from the established frontier.

Preferred sequence:

**ESTABLISHED**
→ **UNRESOLVED**
→ **DEPENDENCIES**
→ **VALIDATION REQUIRED**
→ **NEXT CONTROLLED FRONTIER**

If no next frontier is explicitly established, the AI MUST NOT manufacture one merely because a plausible engineering task exists.

The appropriate next action may be further inspection, validation, clarification, preservation, or deliberate deferral.

---

## 17. Change Discipline

For consequential changes:

**INSPECT**
→ **UNDERSTAND**
→ **PLAN**
→ **CHANGE**
→ **TEST**
→ **RECORD**
→ **HANDOFF**

Before changing:

- establish current Git baseline;
- inspect affected architecture;
- identify semantic owner;
- identify prior registered work;
- preserve unresolved boundaries.

After changing:

- validate;
- run relevant regression checks;
- commit an appropriate checkpoint;
- capture exact Git state;
- synchronize continuity-relevant knowledge;
- verify the continuity update.
